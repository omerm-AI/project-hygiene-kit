# Onboarding acceptance contract v2

V2 replaces the original 512-file/16MiB all-content inventory because a real project has 1,772 files. The original contract remains recoverable in this project's dated `Old/` backup. V2 freezes bounded metadata pages and hashes only explicit transfer candidates.

Runtime exports `run(payload, state_dir, guard_state_dir, *, native_edit=False, command=None)` returning None to continue baseline or native hook JSON. `command` is `(action, body)` after exact standalone parsing. Actions added: onboarding-inventory and onboarding-complete. Handled commands return canonical PreToolUse denial with `accepted by code; no shell command executed` on success. Review/restore remain denied before approval; inspect/read are readonly. Caller passes validated host-protected cwd, native SID and turn/prompt ID. Never accept user-supplied root or native ID. `prompt_suppressed(payload, state_dir)` is readonly. `initialize_empty(payload, state_dir, guide_checker)` is a trusted native UserPromptSubmit entry point.

Operator policy at state_dir/onboarding-policy.json is exactly {schema:1,generation:"v1"}. Absent policy leaves behavior unchanged; malformed/dangling/unsafe policy fails closed at relevant gates. Native agent_id events do not create/promote lead consent. Private state keyed by canonical validated root and bound dev/inode, locked, owner-only, bounded and atomic. Root replacement/cwd escape fails. Do not allow system root, account home or credential/config roots as an organizing project.

The current consent revision (2026-10-25) makes the first delivered existing-root UserPromptSubmit create awaiting-consent once per project/generation and return a native decision:block/reason with a <=200-character Hebrew question and provenance tag/token. This is a client-facing prompt rejection, not additionalContext sent to the model. The original blocked work request must be resent after organization or skip; no full-prompt cache or reinjection is added. Exact next native user prompt `סדר TOKEN` approves and binds organizing owner to that native SID. `דלג TOKEN` skips without project mutation. Free-form yes, quoted/embedded tokens, tool commands, another project's token, stale generation/root, and subagent events cannot approve. Repeated normal or invalid-token prompts in the same native session remain natively blocked with the current question. A new lead session receives a fresh token and invalidates the old token; an organizing owner is never transferred. Stop permits asking without paid automatic continuation. Approved pending organization must not be falsely completed; project work edits are denied until completion. Another native session cannot complete an owner's organizing work. Finished/skipped projects do not ask again on each prompt or session, and ordinary guard review/restore resumes.

Approval is not a bulk move. `onboarding-inventory {}` freezes metadata for at most 5,000 eligible regular, single-link files, with no total-content-size limit or file-content reads. It excludes Old/.git/node_modules/.venv, sensitive/config paths, and only the exact root `FOLDER-GUIDE.md`. Each record has relative path and device/inode/size/mtime/ctime. Sorted private pages hold at most 128 entries and 64KiB each, at most 128 pages; checksum, count, generation and root identity are verified on load. Repeated inventory never replaces a frozen snapshot. Symlinks, hardlinks, overflow, changed metadata and corrupt pages refuse. Large sparse files are inventoried without reading content.

Review entries must belong to the frozen snapshot with unchanged metadata. Only an explicit transfer candidate is hashed just before review and matched to the guard entry. At most 512 transfer candidates are supported; the existing guard retains 128 entries/32KiB per review and a 16MiB per-file candidate bound. Its review performs eligible media/PDF transfers and Old recovery; onboarding edits no project path. Transfers refuse if the guard's reference scan could read excluded sensitive/transcript inputs. Large projects can keep unchanged files in place without claiming they are unused.

`onboarding-complete {}` reloads every page, checks guard pending is clear, and compares a fresh metadata inventory. Every retained original must have exactly unchanged device/inode/size/mtime/ctime; untouched files do not require guard review. Missing originals require matching actual transfer review, candidate SHA-256, original timestamp and verified Old recovery evidence. Asset relocation also requires the exact `Assets/` destination and guard-reviewed hash. Unexpected new or changed eligible files deny completion. Empty explicit inventory can complete. Boolean/prose completion claims do nothing; uncertain files stay in place unless explicitly skipped.

A reviewed superseded/duplicate original may be restored from its exact verified Old manifest during onboarding. Restoration creates the guard's pending postflight requirement. After an explicit keep review, completion accepts changed inode/ctime only when the restored bytes match the frozen candidate SHA, Old manifest and archive remain valid, the restored metadata matches its recorded post-restore signature, and the guard has reviewed that exact hash. Other metadata changes still deny completion.

`initialize_empty` runs only on native lead UserPromptSubmit. It records `finished` with reason `empty-project` only when root has no eligible entries, or exactly one regular root `FOLDER-GUIDE.md` accepted by the trusted caller checker. Only real root `.git` and `Old` directories are ignored in this bounded probe. It neither invents user consent nor organizes existing files. The wrapper independently verifies the managed guide before completion. Existing/nonempty folders use normal consent.

Negative cases before inference: no existing-project moves/scans before consent; lazy/idempotent no-repeat; native decision source and root/token binding; invalid/symlink/oversized private state, pages and policy; same-root two sessions; replay and concurrent updates; unfinished Stop; edits blocked pending and organizing; 1,772+ files and sparse large file without bulk reads; inventory bounds/exclusions; changed/new/missing files and corrupt pages; fabricated completion; eligible duplicate/helper moves and restoration; skipped unchanged root; no history persisted or read from transcripts. Public fixtures contain generic data only.
